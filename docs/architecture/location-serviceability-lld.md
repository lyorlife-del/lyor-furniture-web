# Location and delivery serviceability: low-level design

Designed at LOC-00. LOC-01 implements the manual PIN endpoint, missing-PIN error route, offline importer and opt-in dialog. Other endpoints and later checkout/preference/provider behavior remain proposed. See the [high-level audit](location-serviceability-hld.md) and [implementation gates](../implementation/location-serviceability-plan.md).

LOC-01 uses `app/services/serviceability.py` and `app/services/postal_import.py` rather than a nested package, SQLAlchemy Core tables in `app/db/serviceability.py`, and frozen additive Alembic SQL. The implemented configuration modes are `disabled`, `demo` and `reference`, defaulting to disabled; the UI server flag is `LOCATION_SERVICEABILITY_ENABLED`. The source is not yet approved, so only explicitly labelled synthetic data was exercised. Unavailable decisions use HTTP 503 with the new typed error envelope; eligibility negatives use the documented 200 result. No live fallback or slot claim is made.

## Modules and data flow

Add `app/api/v1/serviceability.py` and `app/services/serviceability/` with postal-reference, eligibility, capacity and preference services. Add `app/integrations/geocoding/` for an async provider protocol, disabled provider, deterministic test provider and Google adapter. Keep domain functions independent of transport and route all writes through existing SQLAlchemy sessions and identity dependencies. Add versioned delivery quote/request modules when LOC-04 starts, reusing pricing, HMAC, owner checks and outbox infrastructure.

Normalize outer whitespace on new PIN inputs, then require ASCII `[1-9][0-9]{5}`; do not coerce integers, strip internal characters or accept Unicode digit lookalikes. A syntactically valid PIN with no row in a complete, healthy reference has `unknown_pin`; unavailable, stale or incomplete reference coverage returns `reference_unavailable` instead of inventing invalidity. Unknown PIN and valid-but-unserviceable PIN are distinct. Existing demo validation retains its accepted error contract.

## New public API contracts

All paths below use `/api/v1`. Define Pydantic v2 request/response models, explicit operation IDs and generated candidate OpenAPI types. Responses use `Cache-Control: no-store` initially. Business negatives return typed results; malformed input uses HTTP 400. Errors retain `statusCode`, `message` and `error`, with additive machine `code` and `retryable` only for new routes. Existing routes and validators must not acquire changed error text or payloads.

| Operation | Input | Response and semantics |
| --- | --- | --- |
| `GET /serviceability/pincode/{pincode}` | Exactly one normalized PIN | 200: `pincode`, `validity` (`valid` or `unknown`), nullable `geography` (country/city/district/state and source version), `deliverable`, nullable `zone`, `reasonCode`, `message`, `configurationVersion`, `checkedAt`, `demo`. City can be unknown without guessing |
| `POST /serviceability/resolve-location` | Strict finite numeric `latitude` [-90,90], `longitude` [-180,180]; optional nonnegative finite `accuracyMeters` | 200: `resolutionStatus`, nullable `pincode`, `ambiguous`, `approximate: true`, `requiresConfirmation: true`, nullable `serviceability`, attribution descriptor. Never fabricate a confidence percentage or persist coordinates |
| `GET /serviceability/slots` | PIN plus ISO `from`/`to` dates; 1–14-day range, Asia/Kolkata calendar; optional owner-scoped cart/quote ID | 200: zone, windows with opaque IDs, start/end instants, `available`/`limited`/`unavailable`, reason and valid alternative windows. Hide internal reserved counts. No inventory or slot hold is created |
| `GET /serviceability/cities` | None | Configured public cities and labels; does not imply every PIN is serviceable |
| `PUT /location-preference` | Confirmed PIN and expected preference revision | Validated preference only; server-visible secure same-site cookie for guests via existing proxy, owner-scoped database preference for authenticated users. Do not store client assertions of eligibility |
| `GET /location-preference` | Existing identity/guest cookie context | Selected PIN and revision; current eligibility is rechecked, not trusted from saved state |

Missing path PIN must not accidentally match a wildcard success route. Duplicate query values, invalid dates, NaN/infinity, booleans as coordinates, oversized bodies and unexpected fields must fail. Unsupported country, missing PIN or distinct plausible PIN candidates produce `outside_india`, `postal_code_missing` or `ambiguous_location`; leave manual correction available. Infrastructure failures return 503/504, client/provider throttles 429/503 as appropriate, never `deliverable: true`. Provider configuration errors are unavailable results with redacted diagnostics.

Stable eligibility reasons: `serviceable`, `unknown_pin`, `outside_coverage`, `zone_disabled`, `zone_paused`, `mapping_inactive`, `mapping_not_effective`, `ambiguous_zone`, `reference_unavailable`. Capacity adds `no_slots`, `slot_full`, `slot_paused`, `slot_expired`. A zone can be serviceable with no slots. Use “Great! LYOR delivers to your area.” only after eligibility succeeds; label synthetic responses as demo. Use “Delivery is not available in this area yet.” for outside coverage, and a separate temporary-pause explanation for paused service.

## Location state and catalogue

LOC-03 implements GET/PUT location preference and GET configured cities. The storefront issues an opaque guest identifier through its same-origin proxy in an HTTP-only, SameSite=Strict cookie, secure on HTTPS. PostgreSQL stores the confirmed preference for both guests and authenticated customers. The API resolves authenticated ownership first. The client uses storage events for cross-tab notification and rereads server state on focus. A previous browser PIN can prefill the selector. Only a server-confirmed preference personalizes catalogue reads.

The opted-in Next.js pages share a request-scoped preference read and use uncached FastAPI catalogue and detail reads with optional `deliveryPin`. The existing Noida route remains a browse entry point. Other city routes are validated against configured cities and require a matching confirmed PIN. Catalogue membership uses the product's city assignments. Detail availability also checks synthetic stock and bundle components. A non-synthetic source cannot use this demo inventory. Cart warnings use a read-only POST to `/serviceability/cart-availability` with the selected lines and existing inventory demand rules. The old signed quote pricing and checkout paths continue to govern transactions.

Extend the existing store with `{pincode, cityId, selectionRevision, confirmedAt}` and ephemeral checking/result states. Restore `lyor-pin-v1` as an unverified preference, not proof of deliverability. Increment a request generation and abort prior work on new input, confirmation, close, sign-out or location change. Browser geolocation callbacks cannot be cancelled reliably: reject callbacks whose generation no longer matches. Do not let an aborted prior request reset a newer request's loading state.

Keep detected candidates separate from confirmed location. Manual Check validates the candidate; an explicit confirmation saves it. Persist confirmed PIN and derived LYOR city only, not Google response objects or GPS. Synchronize PIN changes across tabs, invalidate quote/slot selections and preserve cart lines, variants and tenure. If local storage is unavailable, keep an in-memory preference and explain persistence limitations.

In LOC-03, add optional `deliveryPin` context to FastAPI catalogue/product discovery while preserving old requests and default demo responses. Derive delivery city/zone from the service, never from arbitrary browser city strings. Validate route city against configured cities, preserve filters/search/sort/tenure and refresh server-rendered catalogue via the confirmed preference cookie. Catalogue cache keys include PIN/configuration version; initially keep `no-store`. Return unsupported-item warnings without deleting cart lines. Broaden existing city validation only in the new feature context and keep legacy baseline tests unchanged.

## Quote and checkout contract separation

Do not overload legacy signed payloads or accept optional unsigned slot fields in `/orders`. New `POST /delivery/quotes` accepts owned cart, confirmed PIN and requested slot; new `POST /delivery/requests` accepts that quote's signature, full address, confirmed PIN, slot ID, consent and customer-scoped UUID Idempotency-Key. New DTOs explicitly define city/state/country and supported address fields; normalize and compare against postal and delivery context. A structurally valid address is not proof that a physical doorstep exists. Use the approved address-verification/operations contract when required, and retain `address_unverified` when that evidence is absent.

Use a new quote policy/signature version, binding the delivery context (zone/configuration revision, slot and address validation requirements) in addition to all existing quote fields. Existing `demo-noida-v1` signatures continue to verify through the legacy path. Store the new context in additive extension tables. A location, cart, price, policy or required slot change forces a fresh quote. Repeated successful idempotent submissions return the original request before revalidation; same key with different intent is HTTP 409.

For the local mock ERP, transactionally acquire the zone/configuration lock, quote/cart locks, capacity row and product rows in a consistent order; recheck effective mappings and atomically write the hold, request, outbox and audit. Condition capacity increments on remaining capacity, retry serialization conflicts within a small bound and use constraints as the final duplicate guard. See the [checkout flow](../flows/location-aware-checkout.md).

Odoo and payment cannot participate in a PostgreSQL transaction. Persist a local slot hold and durable request, then use idempotent outbox steps to obtain and reconcile external reservations/payment. Release/compensate holds on definitive failure; uncertain provider results require reconciliation by durable reference, not blind replay. A request is confirmed only when required stock, payment, slot and address evidence exists. Keep unverified live operations gated rather than substituting synthetic stock.

## Administration and expansion interest

LOC-05 adds authenticated `/admin/serviceability` reads and writes using existing admin dependency, optimistic revision checks, company scope and audited before/after changes. Catalogue staff do not automatically receive logistics write permission. Support city/zone listing, PIN membership, effective dates, pauses, capacity inspection and reviewed capacity updates. Every configuration transaction increments the durable configuration revision and records actor/time/reason; public reads cannot write configuration.

Add rate-limited `POST /serviceability/interests` for PIN, minimum contact, explicit consent, preference and idempotency; store no coordinates. Authenticated customers can withdraw their own consent; guests receive a high-entropy opt-out token whose hash alone is stored. Use a response that does not reveal whether a contact is already subscribed. Do not send notifications in LOC-05 without a separately enabled notification contract. Business enquiries are not marketing consent and must not be repurposed silently.

## Reliability and observability

Start PIN/zone queries without an application cache. PostgreSQL remains authoritative; capacity is always reread inside the final transaction. If a measured need justifies Redis caching later, use versioned keys and verify the current durable revision; transactional invalidation events may accelerate eviction but cannot permit stale final decisions. Redis loss may bypass a read cache, while the paid provider limiter fails closed.

Replace the per-process provider quota assumption with a Redis atomic limiter and trusted proxy/client identity handling in LOC-02. Do not trust caller-supplied forwarding headers. Isolate provider limits from unrelated checkout traffic. Add connection pool budgets per Cloud Run instance and max-instance bounds in migration Phase 06. Instrument count, latency, result reason, quota failures and hold conflict/reconciliation rates with low-cardinality labels. Exclude PIN, coordinates, address, contact and secrets from metric labels, traces and request-body logs; redact outbound Google query parameters and exception URLs. Retention and audit access limits require owner sign-off before live activation.
